# ios-a30s: the Galaxy A30s port

This branch (`a30s`) ports [ios-topaz](https://github.com/MakrSas/ios-topaz)
(itself a fork of [ios-sweet](https://github.com/dipa-studio/ios-sweet)) to the
Samsung Galaxy A30s, SM-A307FN, Exynos 7904: 2x Cortex-A73 + 6x Cortex-A53,
GIC-400, eMMC, 720x1560 S6E8FC1 panel. topaz already runs XNU on ARMv8.0
A73 cores only (the A53s have no 16K granule). The Samsung side (S-BOOT boot
image, panel handover, keys, restart reasons) comes from the ztOS port of
this phone (`D:\ios30\ztOS\devices\a30s`). The plan and the hardware map are
in `D:\ios16s30\a30s-port\PLAN.md`.

## Milestone 1: diagnostics shim

`shim/` boots from BOOT, draws on S-BOOT's framebuffer at `0xEC000000` and
answers the questions that decide the port, without any kernel:

| Line | Meaning |
| --- | --- |
| `ENTRY el=` | Exception level S-BOOT enters at (2: the shim drops to EL1) |
| `IMAGE`, `X0 DTB`, `DTB`, `INITRD` | Where S-BOOT puts the image, the DTB and the ramdisk |
| `BOOTCPU` | The core S-BOOT starts on |
| `C000`..`C201` | Each core after PSCI `CPU_ON`: type, `16K:YES/no`, rough clock |
| `A73`, `A53` | `lse` (atomics), `rcpc`, `pan`, `m0` = `ID_AA64MMFR0_EL1` |
| `VERDICT` | Green: the A73s have the 16K granule, XNU can run on them |
| `GICD`, `GICC`, `VTIMER`, `SGI1` | GIC-400 registers; `irqs=` above 0 means the timer and SGIs reach EL1 as Group 1 IRQs |
| `UPTIME`, `KEYS` | Seconds since the results (a reset means a watchdog); live `GPA1` key bits |

Hold Volume Up for a second to restart into TWRP, Volume Down for download
mode. An exception paints a blue panic screen with the same keys.

Build (WSL, with ztOS's toolchain and packer):

```sh
CROSS=~/ztos-build/a30s/toolchain/arm-gnu-toolchain-14.2.rel1-x86_64-aarch64-none-linux-gnu/bin/aarch64-none-linux-gnu- shim/build.sh
```

Flash from TWRP (saves the current BOOT to `shim/out/boot-before-shim.img` first), boot, come back:

```sh
tools/a30s-shim-flash.sh
/mnt/c/platform-tools/adb.exe reboot
# photograph the screen, then hold Volume Up 1 s -> TWRP
tools/a30s-shim-flash.sh --restore
```

### Results on the phone (SM-A307FN, A307FNXXS4CWH1)

**Boot 1 (milestone 1, 2026-10-21), from a photo of the screen:**

- Panel: our text shows, colours right (a8r8g8b8 at `0xEC000000` after the DECON trigger write).
- S-BOOT enters at **EL1** (something owns EL2). `CNTFRQ` = 26 MHz. Image at `0x800D8000`
  (as read off the photo), DTB at `0x8A000000` (size `0x29421`), initrd
  `0x89000000-0x89000014` in `/chosen`. SCTLR_EL1 `0x30C5183E`: MMU off, I on, A (alignment) on.
- Boot core: **A53** `0x100`, MIDR `0x410FD034`, `ID_AA64MMFR0` `0x00001122`:
  **no 16K granule**, no LSE, no RCpc, no PAN.
- GIC-400: GICD IIDR `0x0200143B`, PIDR2 `0x2B` (GICv2), TYPER `0xFCEF` (512 IRQs, 8 CPUs,
  security extensions). **Virtual timer PPI 27: 29 IRQs in 300 ms, self-SGI: 10/10**, as
  Group 1 IRQs at non-secure EL1. The GICv2 path for xnu works.
- Keys idle `GPA1DAT = 0xF6` (bits 5-7 high), `GPA1CON = 0`. Up 42 s without a reset so far.
- **All seven `CPU_ON` returned 0 but no core reported.** Likely Samsung's PSCI 0.1 does
  not deliver the context id in x0: the shim took its stack from x0. The loop clock
  estimate for the boot A53 was ~112 MHz (unexplained; the PMU will tell).

**Boot 2 (milestone 1b):** image at `0x80170000` this time (S-BOOT's load address moves).
Boot A53 at **1014 MHz** by the PMU cycle counter (PMU not trapped). Again every `CPU_ON`
returned 0 and no secondary even set its `arrived` flag, its very first store. So either
the cores never run our code (S-BOOT left the image dirty in the caches and a core
fetching with caches off reads stale memory), or their stores are not visible to the boot
core (data accesses cached with the MMU off, e.g. a hypervisor's HCR_EL2.DC). Milestone
1c cleans the image to memory at entry, does cache maintenance around the reports, and
has each core paint a bar at the bottom of the screen from assembly as soon as it enters.

**Boot 3 (milestone 1c):** no bar below the boot core's: the secondaries never reach
the shim's entry at all. Up 104 s without a reset: S-BOOT leaves no watchdog running.

**From Linux (ztOS) with `tools/a30s-idregs` (2026-10-21):**

- `a30s_idregs.ko`, per core: A53s (MPIDR `0x100`-`0x103`, `0x200`-`0x201`, MIDR
  `0x410FD034`) `ID_AA64MMFR0 = 0x1122`, no 16K granule. **A73s (MPIDR `0x0`, `0x1`, MIDR
  `0x410FD092`, r0p2) `ID_AA64MMFR0 = 0x101122`: TGran16 = 1, the 16K granule is there.**
  No LSE, RCpc or PAN on any core (ARMv8.0), all at EL1. XNU can run on the two A73s,
  as topaz runs on its Gold cores (patch 0081 for the missing instructions).
- Linux brings all seven secondaries up at boot with the same PSCI 0.1 `CPU_ON`
  (entry `secondary_entry` at PA `0x90E56468`, kernel at `0x90000000` from uniLoader).
- A core Linux took offline cannot come back (`CPU7: failed to come online`), and
  `a30s_cpuon.ko` (CPU_ON to a stub, entry `0x888BAC000`) did not start it either: like
  the S9 in ztOS's power notes, a core turned off without Samsung's PMU hint stays
  parked in the firmware. So only cold-boot CPU_ON is comparable with the shim's.

Milestone 1d tries what Linux does differently, one change per core: P1 (C101) one
core at a time with x0 = 0, P2 (C102) + the GIC on, P3 (C103) + the entry in a copy of
the shim at `0x90000000`, P4 (the rest) all of it. Reports go to a fixed mailbox at
`0xEC800000` so a core running from the copy reports to the same place.

**Boot 4 (milestone 1d): all secondaries but one start.**

| Phase | Core | Change | Arrived |
| --- | --- | --- | --- |
| P1 | C101 | one at a time, x0 = 0 | no (stays parked, even after the GIC is on) |
| P2 | C102 | + GIC distributor and CPU interface on | **yes** |
| P3 | C103 | + entry in a copy at `0x90000000` | yes |
| P4 | C200, C201, C000, C001 | all of it | 4/4 |

- **The GIC must be on (GICD_CTLR EnableGrp1, GICC_CTLR, PMR) before `CPU_ON`**, as Linux
  has it. Without it the firmware accepts `CPU_ON` (returns 0) and leaves the core parked
  for good. The entry address does not matter.
- **x0 on arrival is `0x0204901C` for every core, not the context id**: the core number
  has to come from MPIDR (xnu's `sweet_secondary_entry` reads it from x0: to change).
- A73s (C000, C001): `16K:YES`, MMFR0 `0x101122`, EL1, **~1352 MHz** after `CPU_ON` (max is
  1768 MHz: DVFS through ACPM later). A53s at 1014 MHz.

### What this means for the XNU port

- XNU runs on the two A73s only. The shim (on the A53 boot core) turns the GIC on, wakes
  A73 `0x0` with `CPU_ON` and hands off there, as topaz does with its Gold core.
- GICv2 (GIC-400) works for timer and SGIs as Group 1 IRQs at non-secure EL1: XNU needs a
  GICv2 path instead of topaz's GICv3 one.
- Secondary entry: core number from MPIDR (A73: Aff1 = 0, core = Aff0).

Milestone 1b takes the core number from MPIDR, shows the x0 each core arrived with
(`PSCI` line: whether xnu's `sweet_secondary_entry`, which reads the cpu number from
x0, needs MPIDR instead), records secondary crashes, and measures the clock with the
PMU cycle counter. QEMU `virt` run: EL2 entry, EL1 drop, a second core with
`x0 = context id`, PMU readable.

Controller facts used (checked in mainline `dw_mmc*.c` and Samsung's kernel, see Places): dwmmc0 at
`0x13500000`, Exynos 7 flavour with the SMU (`exynos7-dw-mshc-smu`); FIFO 64 entries x 64 bit = 512
bytes, data register at `+0x200` (VERID >= 0x240a); `CLKSEL64` at `+0xA8` (drive phase != 0 ->
`CMD.use_hold_reg`); SMU region 0 at `+0x1200/0x1204/0x120C`; 64-bit IDMAC layout (`IDSTS64` `+0x90`,
`IDINTEN64` `+0x94`). Stock Android runs the card in HS400 enhanced strobe with command queueing;
ztOS's mainline in HS200.

What 0145 does:
- **Take over S-BOOT's host, never re-init:** print the registers (and S-BOOT's last command); require
  VERID "SB", the card clock on and a 32/64-bit FIFO; interrupts off, IDMAC torn down the Linux way
  (DMA reset, `BMOD` soft reset, `IDSTS64` cleared), FIFO reset, `TMOUT` max; SMU region 0 set to
  normal-world read/write over the whole card if it is not already (mainline's values). No controller
  reset, no clock, bus width or timing change.
- **Card:** CMD13 with RCA 1 (then 2, 3), CMD7 if it is in standby; CMD8 EXT_CSD (retried with
  command queueing off if refused); HS200/HS400 -> card read threshold 512 (`CDTHRCTL`); command
  queueing off (EXT_CSD[15]); `PARTITION_ACCESS` back to the user area if needed (boot bits kept).
- **Transfers:** CMD23 + CMD18/CMD25 (CMD17/CMD24 for one sector); each 64-bit FIFO entry moved as two
  32-bit accesses (Samsung's `MMC_DW_FORCE_32BIT_SFR_RW`); wait for DTO; writes wait for the card's busy
  and check CMD13 is back in transfer state; any error -> CMD12 + FIFO reset. Sync = EXT_CSD
  `FLUSH_CACHE` when the card cache is on.
- **Upper layers:** 4 KiB device blocks = 8 sectors; the GPT is read per 512-byte sector; the partition
  must start 4 KiB aligned (its end is cut to whole blocks); writes are refused below block 6 and from
  the backup GPT entries up (`gpt_fence`), and without `ufsrw=1`.

Boot-args: `rd=ufsroot0` (root on the GPT partition `ufsroot=`, default `userdata`), `mmchold=1` (stop
after the probe: no root mount and no panic, so the lines stay on the screen), `mmcgpt=1` (print every
GPT entry, about 32 lines), `ufsrw=1` (writes; not before the read-only test passed).
